Why we need our own data types

Monday, 8:00 a.m. Bea drops a stack of paper forms on your desk. "Java knows numbers and words," she says. "I need it to know about dogs. Oh, and paint colors for the kennel signs."

Java gives you built-in types like int, double, boolean and String. They are great for numbers and words, but the world is full of other things: colors, cars, buildings, robot states, sensor readings.

We want to say Color mix = red.mix(yellow); and get orange. OOP lets us invent the type Color and teach it what mix means.

Abstract Data Type (ADT)

An ADT is a type described by what you can do with it, not by how it works inside. You drive a car with a wheel and pedals; you do not need to know how the engine is built. That is abstraction.

Real life is objects talking to each other

A person orders coffee from a shop; a dog follows its owner across the street at the traffic light. Big programs are built the same way. In a video game nobody thinks "instruction 4,512"; they think of cars, characters and traffic lights, each with its own data and behavior. That is OOP: model the software the way you already think about the world, so large programs stay organized and each object looks after itself.

OOP is one style among several

ProceduralA list of steps run top to bottom. Example: C.
Object-orientedObjects with data and behavior that talk to each other. Example: Java.
FunctionalPrograms built from functions that take values and return values. Example: Haskell.

These styles are called programming paradigms. Most modern languages mix them: Java is mainly object-oriented, with functional features too.

The problem: a camp with 100 dogs

Monday, 10:00 a.m. Your first try: six arrays, one per fact. By lunch, Luna has been credited with Bella's visit, and Bella's owner is on the phone. Try the typo button to see how it happened.

You run a dog-sitting camp. For every dog you track a name, breed, color, weight, age and days attended. 100 dogs × 6 facts = 600 facts.

Without a class you keep six separate arrays, one per fact. Dog number 3 is "whatever sits at index 3 in all six arrays". One wrong index and you update the wrong dog, with no error message.

With a class each dog's facts live together in one bundle, and the actions (like checkIn()) are attached to that bundle. There is no index to mistype.

Key insight: a class does not delete information. We still have 600 facts. It organizes them so each dog's details stay together. Write the description once, make many dogs.

Overloading: several ways to check in a dog

  
Wednesday, 11:00 a.m. A stray wanders in with no collar. Ten minutes later a dog arrives whose owner only knows his name. Your constructor demands three answers. Now what?

  
A class can have several constructors with the same name, as long as their parameter lists differ (in number, types or order). Java looks at the arguments you pass and picks the one that matches.

  
Not allowed: two constructors with the same parameter types. Parameter names don't count.

  
The free default constructor

  
If you write no constructor at all, Java quietly adds public Dog() { }. Fields then start at default values:

  
Field typeDefaultExample

   
int, long0age, daysAttended

   
double0.0weight

   
booleanfalsevaccinated

   
String, any objectnullname, breed

  

  
Gotcha: once you write any constructor, the free one disappears. If Dog only has Dog(String, String, int), then new Dog() is a compile error. Write public Dog() { … } yourself if you want it.

toString(): how an object prints itself

  
Thursday, 9:00 a.m. You print the attendance sheet for Bea. It reads Dog@1b6d3586. "Who," she asks slowly, "is Dog@1b6d3586?"

  
When you write System.out.println(daisy) or glue an object onto a String with +, Java secretly calls daisy.toString().

  
Every class gets a default toString(), but it is not helpful: it prints the class name, an @, and a hash code in hex, like Dog@1b6d3586. The number changes from run to run.

  
So we write our own and override the default. You decide what a dog looks like as text.

  
"Tag: " + daisy works because one side is a String. String s = daisy + 7; does not compile: neither side is a String, so Java won't call toString().

static: one copy for the whole class

  
Thursday, 3:00 p.m. Bea asks a simple question: "How many dogs are at camp right now?" Whose job is it to know? Not Daisy's. Not Max's.

  
Normal fields belong to each dog: every dog has its own name. A static field belongs to the class itself: there is one shared copy, and it exists even when there are zero dogs.

  
Perfect for "how many dogs are at camp?" Nobody's personal tag should hold that number. You've used static members before: Math.PI, Math.sqrt(2.0). You call them on the class name, not on an object.

  
Instance methodStatic method

   
Belongs toeach objectthe class itself

Rule of thumb: if the method needs to know which dog, it is an instance method. If any dog, or no dog, will do, it can be static. Think: the shop's opening hours (static) vs. the contents of your basket (instance).

Encapsulation: lock the data, open the methods

  
Friday, 9:00 a.m. Alarm at the vet's office: Daisy's file says she is −500 years old. An intern typed daisy.age = -500; and nothing stopped him.

  
Think of a capsule: the dog's data on one side, its methods on the other, sealed into one unit (the class). Then we lock the data with private. Outside code can only reach it through public methods, which check every change.

  

   
 Fields: private
  • name
  • breed
  • age

   
Methods: public
  • getAge()
  • setAge(int)
  • bark()

  

  
Why bother? Two problems with public fields

  
    
   
  • They accept nonsense. daisy.age = -500; compiles. Nothing stops it.
    • 
   
  • They lock in your design. Decide later to store birthYear instead of age? Every file that wrote daisy.age breaks. With a getter, only Dog.java changes.
    • 
  

  
Getters and setters

  
Getter (accessor) getAge() returns a field. Setter (mutator) setAge(int) changes it after checking. Not every field needs a setter: a dog's breed never changes, so it stays read-only.

  
Two more good habits: write a comment above each public method so users know how to use it, and make any helper methods private too.

  
You've seen this on the rover: rover.setSpeed(...) clamps every value to 0–100 before touching the motors. That's Lab 9's clamp() helper doing the checking.

Inheritance: write shared code once

  
Friday, 3:00 p.m. Bea bursts in: "Big news! Starting Monday we take cats too." You picture copying all of Dog.java into Cat.java, and shudder.

  
The camp now takes cats too. Dogs and cats share a lot: id, name, age, getName(), checkIn(). Copying that code into both classes means fixing every bug twice.

  
Instead, put the shared parts in a superclass (parent) called Pet. Then Dog and Cat extend it and add only what is new.

  

  
    
   
  • extends Pet: Dog gets Pet's fields and methods.
    • 
   
  • super(id, name, age): run Pet's constructor to set up the inherited part. Forget it and you get "constructor Pet in class Pet cannot be applied to given types".
    • 
   
  • Pet's private fields are inside every Dog, but Dog's code must use getters to reach them.
    • 
  

  
The "is-a" test: use extends only when "a Dog is a Pet" is true. A Dog has a name, so name is a field, not a parent class.

  
Slides 106–114. Every class secretly extends Object; that's where the default toString() and equals() come from.

Overriding: same method, the child's own version

  
Friday, 4:30 p.m. First test run with cats: Tom the cat "makes a sound". So does Daisy. Bea: "Dogs bark. Cats meow. Fix it."

  
Pet has speak() that prints "makes a sound". That's fine as a fallback, but a dog should say Woof and a cat should say Meow. A subclass can override an inherited method: same name, same parameters, new body.

  
Put @Override above it. It asks the compiler to check that you really are replacing a parent method. A typo like speek() then becomes a compile error instead of a silent bug.

  
Look at the loop on the right: one line, pets[i].speak(), and each pet answers in its own way. That idea is called polymorphism, the fourth pillar, coming in OOP part 2.

Generics: one box for any cargo

  
Season two, week 1. Bea orders storage boxes: one for treat counts, one for name tags, one for whole dog records. You start typing IntBox, StringBox, DogBox… and realise you are writing the same class again and again with one word changed.

  
Remember overloading? One method name works with many parameter types, so Java can have one add. C has no overloading, so it needs separate names: abs, fabs, labs…

  
Generics bring that idea to whole classes. Write the class once with a type parameter T, a blank label that gets filled in when you use the class:

  

  
    
   
  • Reuse: one Box class for every type, so fixing one bug fixes them all.
    • 
   
  • Type safety: a Box<String> only accepts Strings. Mistakes are caught when you compile, before the program runs, and you never need casts.
    • 
   
  • By convention a type parameter is one capital letter: T for type, E for element.
    • 
   
  • Two are fine too: public class Pair<S, T> holds two things of different types.
    • 
   
  • Inside the class, use T like a real type, with one exception: you can't write new T().
    •

Wrapper classes: gift-wrapping a primitive

  
Week 1, Tuesday. You try Box<int> for the treat counts. javac refuses: unexpected type; required: reference; found: int. Generics only hold objects, and int is not an object.

  
A primitive is a bare value. A wrapper is the same value gift-wrapped inside an object. Every primitive type has one:

  
int → Integerdouble → Doublechar → Characterboolean → Booleanlong → Longfloat → Floatbyte → Byteshort → Short

  
Primitive intWrapper Integer

   
Memory4 bytesabout 16 bytes (object header + value)

   
Speedfastesta little slower

   
Fits in genericsnoyes: Box<Integer>

   
Use it forperformance-critical codewhen you need object features

  

  
You already know how to read this class

  
Integer is a normal class with the parts you know. Fields: Integer.MAX_VALUE is 2,147,483,647 (231 − 1) and MIN_VALUE is −231, straight from the two's complement chapter. Methods: Integer.parseInt("42"), Integer.compare(a, b). It even has constructors, but new Integer(5) is deprecated; write Integer x = 5; instead.

  
Autoboxing and unboxing

  
Java wraps and unwraps for you. Autoboxing: Integer obj = num; puts the int in a box. Auto-unboxing: int p = obj; takes it back out. No new, no .intValue() needed.

  
Gotcha: wrappers are objects, so == compares arrows, just like Dogs. Integer a = 1000, b = 1000; then a == b is false. Use a.equals(b). (Small values from −128 to 127 are cached, so == happens to work there, which makes this bug sneaky.)

Arrays of objects: a kennel for many dogs

  
Week 2. The new kennel building has five kennels. You write Dog[] kennel = new Dog[5];, walk over to greet the dogs… and all five kennels are empty.

  
An array of objects is an array of arrows. new Dog[5] builds five slots, and each starts as null, meaning "no dog here yet". That line creates zero Dog objects. Every dog still needs its own new.

  
    
   
  • kennel[0] = new Dog("Daisy", 3); builds a dog and stores its arrow in slot 0.
    • 
   
  • Dog[] dogArray = {daisy, balto}; makes an array that copies the arrows of dogs you already have.
    • 
   
  • for (Dog d : kennel) visits every slot, empty ones included.
    • 
  

  
Calling a method through an empty slot crashes the program with a NullPointerException: there is no dog to bark. Check if (kennel[i] != null) first.

Why sort? To find things fast

  
Week 3, Monday. A parent calls: "Is tag 72 registered?" Bea's list holds 16 tag numbers. You could check them one by one… or be clever, because the list is sorted.

  
Linear search checks items one by one from the left. It works on any array, sorted or not, but in the worst case it checks every item.

  

  
Binary search is how you use a phone book. Looking for "Max"? Open the middle, see "L", ignore the left half. Each look throws away half of what's left. It only works because the list is sorted.

  

  
Items nLinear: up to nBinary: about log₂ n

   
16165

   
1,0001,00010

   
1,000,0001,000,00020

   
1,000,000,0001,000,000,00030

  

  
Double the items: linear search does double the work, written O(n). Binary search does one more step, written O(log n). The catch: the data must be sorted first. Sort once, then search fast many times; databases keep sorted indexes for exactly this reason.

  
Part 2 slides 19–27. Fine print: for giant arrays, lo + (hi - lo) / 2 avoids the int overflow that (lo + hi) / 2 can hit.

Is log n a big deal? Ask the ants

  
Week 3, Tuesday. Bea shrugs: "20 steps or a million, computers are fast." So you set up a race between two ants.

  
Put the items in a line, 1 cm apart. Both ants walk at 1 cm per second.

  
    
   
  • The linear ant walks the whole line: n cm, so n seconds.
    • 
   
  • The binary ant only climbs the height of the triangle: log₂ n cm, so log₂ n seconds.
    • 
  

  
Why a triangle? Each step of binary search halves the range, so a search tree of height m covers 2m items. Width n, height log₂ n: same triangle, two very different walks.

  
Drag the slider all the way up. log₂ n grows so slowly it is almost constant in practice: searching every atom in the universe takes the binary ant 266 seconds. The price to pay is keeping the data sorted.

Sorting objects: Java needs a rule

  
Week 4, agility show. Bea wants the dogs lined up youngest first. Sorting numbers worked last week, so you confidently type Arrays.sort(dogs);. The program crashes.

  
Sorting isn't only for searching. Sorted data lets you see patterns at a glance (the youngest and oldest dog sit at the two ends, duplicates sit side by side, similar items cluster), and people expect order: products by price, emails by date, rankings top to bottom.

  
Arrays.sort (from java.util.Arrays) already sorts numbers and Strings, because Java knows what "smaller" means for them: 1 < 2, and "Alice" before "Bob". For Dogs, smaller by what? Age? Name? Days at camp? Java can't guess, so it refuses.

  
Interfaces: a formal promise

  
An interface is a list of methods that any class implementing it must contain. An API is an informal promise; an interface makes it formal, and javac checks that the class keeps it. Any client can then rely on those methods being there.

  
java.lang.Comparable<T> lists exactly one method: int compareTo(T o). Promise it, and Arrays.sort will accept your Dogs:

compareTo: thumbs down, level, or up

  
Still week 4. Bea: "Youngest first. And when two dogs are the same age?" Time to write the rule, and to decide what happens in a tie.

  
this.compareTo(that) returns an int, and only its sign matters, like a thumb:

  

   
−negative: this goes before that

   
0zero: a tie, same rank

   
+positive: this goes after that

  

  
−100 and −1 mean exactly the same thing: "before". You asked which is bigger, not by how much.

  
Pro tip: don't subtract

  
Slides often write return this.age - that.age;. That's fine for dog ages, but with huge values the subtraction can overflow (two's complement again!) and flip the sign, and the sort is silently wrong. Integer.compare(this.age, that.age) is always safe. Try the overflow button in the toy.

  
Ties

  
Three dogs aged 3: who goes first? Arrays.sort on objects is stable: tied dogs keep their original order. To decide yourself, break the tie with a second rule (name, then tag id). Every option is predictable; it just answers "who goes first?" differently.

  
Part 2 slides 50–55. For names, this.name.compareTo(that.name) uses String's own rule: dictionary order, with capitals before lowercase.

Polymorphism: one call, many types

  
Closing ceremony. Bea grabs the microphone: "Everyone, speak!" One instruction, and every animal answers in its own way. That's the fourth pillar.

Inheritance does the same thing. A Dog is a Pet, so a Pet variable can point at a Dog:
